01The journey, step by step

Each step was planned, approved, implemented, tested and recorded before the next one started. Every choice marked provisional is still open in the decision log.

Phase 0 · Foundation

Repository, API skeleton, CI

Python 3.11 + FastAPI with a /health endpoint, typed settings from MEDRAG_* variables, pinned dependencies, ruff, pytest, GitHub Actions, local OpenSearch 3.8.0 in Docker. No secrets in Git.

Phase 1 · Corpus

100 approved public documents

70 DailyMed drug labels, 15 PubMed Central open-access articles, 10 FDA approval letters, 5 NIH LiverTox monographs. URL, version, date, licence basis and SHA-256 kept for every file; original files never modified; no patient data.

Phase 2 · Parsing and chunking

One parser per source, structure-aware chunks

SPL (labels), JATS (PMC), LiverTox NXML and FDA PDF parsers; shared text normalisation; four chunking experiments (overlap 0/32/64/96 tokens). Result: 5,815 chunks with deterministic IDs.

Phase 3 · Search and answers

Embeddings, hybrid search, grounded answers, chat UI

bge-base-en-v1.5 embeddings, one OpenSearch index with BM25 text and HNSW vectors, rank fusion (RRF), Claude Sonnet 5.5 answers that cite passage ids or abstain, the Beyond Doc chat UI with history (ClickHouse) and memory (Redis).

Evaluation v1 → v2.0

From a drafted test set to a frozen, reviewed one

First 145 drafted questions, then a reviewed v2.0 set of 150 questions with evidence passages, frozen and split 75 dev / 75 holdout. Design decisions use dev only; holdout runs once at the end.

Phase 4 · Reranking trial

Cross-encoder reranker tested and rejected

MiniLM-L6 reranking of the top 20 / 40: small ranking gain, 3.6 s added per question on CPU, and clinically wrong reorderings. Not adopted (details below).

Retrieval v1.2

Medicine-, source- and section-aware search (preset T3)

Four deterministic rules on top of hybrid search, chosen by comparing eight variants on dev and confirmed once on holdout.

Answer prompts v1 → v4.1

Polite, step-by-step, cited, and safe on doses

Five prompt versions tested end to end with Ragas; v4.1 answers related information instead of refusing, and never gives doses for uses the documents do not cover.

Deployment

A Linux server behind nginx, password protected

Own OpenSearch, Redis and ClickHouse containers on local-only ports, a systemd service, and an nginx /medrag/ location with basic auth. Same index and same results as the laptop.

02Chunking: the steps

Raw XML / PDF→Parse to sections→Normalise text→Split recursively ≤ 510 tokens→Add overlap→Prefix + metadata→Validate
  • Structure first. Chunks follow the document's own sections (for example 8.6 Renal Impairment, Case 2, Results). A chunk never mixes two sections.
  • Recursive splitting. When a section is too long it is split at the largest natural boundary that fits: block, then table rows, labelled cells, sentence, clause, phrase. In the corpus: 4,342 block splits, 759 row splits, 659 labelled-cell splits, 243 sentence splits.
  • Token ceiling. 510 content tokens counted with the BERT uncased tokenizer, which has the same vocabulary as the embedding model, so 0 of 5,815 chunks are counted differently from what the model sees.
  • Tables kept as tables. 1,411 table chunks in pipe format; 44 header rows inferred and flagged, 117 tables without headers flagged.
  • Excluded on purpose. SPL Highlights (318 blocks, duplicates of the full label), package-label images (172), empty blocks (103).
  • Provenance on every chunk. Document id, version, section path, section role (body, case report, bibliography…), medicine names, source URL; chunk id = SHA-256 of its content and position.

04How a choice was judged better

Every comparison uses fixed questions with known evidence passages, the same corpus and index, and one change at a time. Retrieval is scored without any LLM; answers are scored with Ragas.

Retrieval metrics (no LLM)

  • Evidence recall@8: share of the needed evidence that reaches the 8 passages sent to the model.
  • AP@8, MRR, nDCG: how high the evidence ranks.
  • Wrong-medicine passages: passages about another drug in the top 8.
  • Latency: P50 / P95 per stage.

Answer metrics (Ragas)

  • Faithfulness: every claim supported by the passages.
  • Answer relevancy, claim recall, factual precision.
  • Context precision / recall as judged.
  • Abstention: unanswerable questions refused; answerable ones never refused.

Step 2: the reviewed v2.0 set (150 questions, frozen, 75 dev / 75 holdout)

Single-document, multi-document, interaction, pharmacology, LiverTox, PMC, FDA and unanswerable categories, each with evidence passages checked against the chunks. All later choices were made on dev; holdout ran once.

05Document-aware retrieval (Retrieval v1.2, preset T3)

Rule 1

Medicine resolver

A corpus-built alias table maps brands, generics and salt forms (Lipitor → atorvastatin) to that medicine's documents. No LLM, no invented brand–generic links.

Rule 2

Medicine boost

Soft keyword boost for the medicine's documents plus an extra vector search limited to them, fused with the normal results.

Rule 3

Source coverage

When a question names two sources ("the label" and "LiverTox"), each source gets its own search and at least 2 of the 8 places.

Rule 4

Section awareness

Reference lists, signatures and patient-leaflet tables move down (never removed); the section matching the question (Dosage, Adverse Reactions…) gets a small boost.

  • Too slow on CPU: 3.6 s median against a 0.5 s budget, about 10 times over; MedCPT's cross-encoder is about 5 times heavier.
  • Clinically wrong reorderings: one interaction question ranked another drug's label first; LiverTox reference lists outranked the clinical overview.
  • No recall gain: a reranker only reorders the candidates; it cannot bring in evidence that never reached them. The misses were coverage problems, which T3 fixes directly.

The two wrong-medicine rows use different medicine groupings (Phase 4's first grouping, then the v1.2 alias table), so compare within a row only. The reranker code stays in the repository for a future GPU trial.

08System design for heavy traffic, with control

Today one server and one OpenSearch node serve a password-protected demo. Growing to thousands of users needs every stage to scale on its own and every expensive call to be capped, queued and observable, so a traffic spike slows the system down gracefully instead of failing.

Controls that stop overload

  • Edge rate limits per IP and per user (load balancer / nginx), on top of today's 20 questions per minute per user.
  • LLM gateway with a global concurrency cap, a short queue, retries with backoff, and a clear "busy, try again" (the 503 path already exists).
  • Per-user daily quotas in Redis; sign-in before quotas are raised.
  • Answer cache for repeated questions (same question + same index + same prompt version).
  • Load shedding: skip the follow-up rewrite and serve retrieval-only results when the queue is long.

Scaling each stage

  • API: stateless pods, autoscaled on CPU and open streams.
  • Embedding: its own service, batched, on ONNX or a small GPU (today about 145 ms of each search).
  • OpenSearch: 3 nodes with replicas; new index built offline, then the alias switched (already how indexing works).
  • Chat history writes asynchronous; Redis managed with failover.
  • Secrets in a secret manager, never in images.

09Local and web give the same answers

The web deployment matches the laptop because both run the same commit, the same 5,815-chunk index built from the same embeddings, the T3 retrieval preset and prompt v4.1. Three test searches returned exactly the same top 8 chunks on both machines (byte-identical result files). Retrieval is deterministic; the answer text can vary slightly in wording between runs because it is generated, while citations come from the same passages.

10Known limits and open decisions

  • Coverage is 70 medicines; anything else is refused or answered only from mentions inside other labels.
  • The v1.2 rules were designed on dev failures; the holdout check (68 answerable questions) is small.
  • Passage choice inside the right document still fails on a few questions (q077, q080, q083).
  • Not yet benchmarked: chunk overlap amount, MedCPT embeddings, vector algorithm at scale, learned sparse search, rerankers on GPU.
  • Demo hosting is a single server with password access; nothing is load-tested, and there is no production hardening.
